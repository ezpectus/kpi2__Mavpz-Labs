# Audit: Lab 3 - Sequence Diagram

## Метод

Порівняв sequence-діаграму з spec.md, UC3 (Lab 2) та ER-моделлю (Lab 1). Кожна розбіжність: який критерій у spec був неточним/відсутнім -> як уточнив -> коміт-виправлення. Топ-3 за шаблоном завдання — №1–3; №4 знайдено при фінальному рев'ю власною симуляцією чека й додано чесно окремо.

## Знайдені розбіжності

### 1. Один учасник "Server" замість конкретних компонентів + немає return-повідомлень

**Критерій spec:** «основні компоненти/об'єкти» + «return-повідомлення» — були в spec від `faabc11`; формулювання «компоненти — окремі lifelines (не один Server)» уточнено комітом `eec9c72`.
**Знайдено:** перша версія мала один учасник "Server" і тільки запити (->>) без відповідей — не видно, який компонент за що відповідає.
**Виправив:** розбив Server на VideoController, AuthService (UC9 з Lab 2), VideoService, Database (Video entity з Lab 1); додав -->> для всіх викликів.
**Коміт-модель:** `5395f87` — fix - split server into components + return messages

### 2. Немає альтернативних/помилкових гілок

**Критерій spec:** «альтернативні/умовні гілки» і «гілки помилок (401, 400, 409)» — з `faabc11`, уточнено `eec9c72`.
**Знайдено:** діаграма показувала тільки happy path.
**Виправив:** додав alt (token invalid/valid) з 401, гілки 400 і 409.
**Коміт-модель:** `2efea96` — fix - add alt/opt error branches

### 3. opt для термінальних помилок + неочевидний userId у createVideo

**Критерій spec:** «гілки помилок завершують сценарій» існував, але словами; уточнено до явного правила «ТЕРМІНАЛЬНІ (alt, не opt)» комітом `eec9c72`. Узгодженість з ER (authorId) — критерій з `faabc11`.
**Знайдено:** (a) гілки 400/409 стояли як `opt` — opt не обриває сценарій: після 400/409 потік міг продовжитись до 201. (b) `createVideo(userId, ...)` — в ER поле `authorId`; userId з токена стає authorId, але з назви це нечитається.
**Виправив:** вкладені `alt/else` (кожна помилка — термінальна гілка, успіх тільки у else-ланцюжку), validateToken винесено перед alt (один виклик), параметр `authorId = userId`.
**Коміт-модель:** `9c345cb` — fix - alt for terminal errors + authorId naming

### 4. Дедуп як неявний конфлікт БД замість явного кроку (знайдено при фінальному рев'ю)

**Критерій spec:** відсутній — додано «кроки бізнес-правил — явні повідомлення: дедуп-перевірка findByAuthorAndUrl перед createVideo».
**Знайдено:** Database відповідав `conflict` на `createVideo` — це виглядало як UNIQUE-обмеження в БД, а ADR-003 каже: дедуп — правило рівня застосунку (в ER такого UNIQUE немає). Неявний крок суперечив власному ADR.
**Виправив:** явна перевірка `findByAuthorAndUrl(authorId = userId, url)` перед створенням; гілки — `conflict` (дублікат) / `not found` -> `createVideo` -> `videoId` -> 201.
**Коміт spec+модель:** `eec9c72` — spec+model - explicit dedup check step + sharpened criteria (один коміт змінює і критерій в spec, і діаграму)

### 5. Вкладена піраміда alt/else замість лінійних термінальних фрагментів (знайдено при рев'ю викладача)

**Критерій spec:** «гілки помилок ТЕРМІНАЛЬНІ» існував; формулювання уточнено до «break-фрагменти (вихід зі сценарію)» — термінальність тепер виражена явним оператором, не структурою вкладення.
**Знайдено:** помилки 401/400/409 були змодельовані вкладеним alt/else в 4 рівні — семантично коректно, але рамки займали всю діаграму і читались як «альтфлоу всюди». Успішний шлях був похований у найглибшому else.
**Виправив:** плоска структура — лінійний основний потік + три `break`-фрагменти для термінальних помилок (break = виконати гілку і перервати решту сценарію — точна семантика термінального виходу). Семантика ідентична вкладеному alt, читабельність у рази краща; validate input винесено явним кроком контролера.
**Коміт spec+модель:** цей коміт (spec.md, sequence.mmd, sequence.drawio, renders/sequence.png)
