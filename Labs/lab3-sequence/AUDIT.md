# Audit: Lab 3 - Sequence Diagram

## Метод

Порівняв sequence-діаграму з spec.md, UC3 (Lab 2) та ER-моделлю (Lab 1). Топ-3 розбіжності + коміти-виправлення.

## Знайдені розбіжності

### 1. Один учасник "Server" замість конкретних компонентів + немає return-повідомлень

**Знайдено:** перша версія мала один учасник "Server" і тільки запити (->>) без відповідей. Spec вимагає "основні компоненти/об'єкти" і "return-повідомлення". Не видно, який компонент за що відповідає і що система повертає.

**Виправив:** розбив Server на VideoController (прийом запиту), AuthService (валідація токена, UC9 з Lab 2), VideoService (бізнес-логіка), Database (Video entity з Lab 1). Додав return-повідомлення (-->>) для всіх викликів.
**Коміт:** `5395f87` — `fix - split server into components + return messages`

### 2. Немає альтернативних/помилкових гілок

**Знайдено:** діаграма показувала тільки happy path. Spec вимагає "альтернативні/умовні гілки" і "гілки помилок (401, 400, 409)".

**Виправив:** додав alt (token invalid vs valid) з 401, гілки для 400 і 409.
**Коміт:** `2efea96` — `fix - add alt/opt error branches`

### 3. opt для термінальних помилок + неочевидний userId у createVideo

**Знайдено:** на самоперевірці помітив дві речі. (a) Гілки 400/409 стояли як `opt` — а `opt` не завершує сценарій: після 400/409 потік міг продовжитись до створення Video і 201. Spec каже "гілки помилок завершують сценарій". (b) `createVideo(userId, ...)` — в ER (Lab 1) поле називається `authorId`; userId з токена стає authorId, але з назви параметра це нечитається.

**Виправив:** замінив `opt` на вкладені `alt/else` (кожна помилка — окрема термінальна гілка, успіх тільки у else-ланцюжку), виніс validateToken перед alt (один виклик замість двох), перейменував параметр у `createVideo(authorId = userId, ...)`.
**Коміт:** `9c345cb` — `fix - alt for terminal errors + authorId naming`
