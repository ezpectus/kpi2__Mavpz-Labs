# Use Case описання — VideoHub

Повний опис діаграми (`model/usecase.puml`, рендер `renders/usecase.png`): кожен актор, кожен UC і кожне відношення + сценарії потоків.

## Актори

| Актор | Тип | Опис | UC |
|---|---|---|---|
| Guest | Людина | Неавтентифікований відвідувач | UC1, UC2, UC4, UC8 |
| User | Людина | Автентифікований юзер; спеціалізує Guest (успадковує UC4, UC8) | UC3, UC5, UC6, UC7 (+ успадковані) |
| Google OAuth | Зовнішня система | Провайдер автентифікації | UC9 |

**Узагальнення** `User --|> Guest`: User — спеціалізація Guest (стрілка дитина→батько). User має всі можливості Guest + власні user-only дії. Тому Register/Login асоційовані з Guest, не User.

**Межа системи** `VideoHub System`: усі UC всередині; актори зовні. Google OAuth — зовнішня система, бере участь у UC9.

## Відношення на діаграмі

| Відношення | Від → До | Семантика |
|---|---|---|
| association | Guest → UC1/UC2/UC4/UC8 | Guest ініціює ці UC |
| association | User → UC3/UC5/UC6/UC7 | User ініціює ці UC |
| association | Google → UC9 | Google бере участь у автентифікації |
| generalization | User —▷ Guest | User спеціалізує Guest |
| «include» | UC2/UC3/UC5/UC6/UC7 ⇢ UC9 | базовий UC ЗАВЖДИ викликає UC9 (auth) |
| «extend» | UC8 ⇢ UC4 | UC8 ОПЦІЙНО розширює UC4 (пошук→перегляд) |

## Сценарії UC — основний потік + альтернативні

Формат: **Основний потік** (main flow — успішний сценарій по кроках), **Альтернативні потоки** (A1, A2... — відгалуження від конкретного кроку: помилка, скасування, інший вибір).

### UC1 Register — актор: Guest — REQ1

**Мета:** створити акаунт email/password.

Основний потік:
1. Guest відкриває форму реєстрації.
2. Вводить email, username, password.
3. Система валідує дані.
4. Система створює запис `User` (ER: User.id, email UK).
5. Система повертає auth token.

Альтернативні потоки:
- **A1** (крок 3): email зайнятий → система повертає помилку, просить інший.
- **A2** (крок 3): слабкий пароль → повідомлення про вимоги.

### UC2 Login — актор: Guest — REQ2

**Мета:** увійти (credentials або Google).

Основний потік:
1. Guest обирає спосіб входу.
2. Система включає UC9 Authenticate («include»).
3. Система повертає session/token.

Альтернативні потоки:
- **A1** (крок 2): Google OAuth — редірект на Google, callback → create/find акаунт (REQ2).
- **A2** (крок 2): невірні credentials → помилка, кінець.

### UC3 Upload Video — актор: User — REQ3, REQ11

**Мета:** опублікувати відео.

Основний потік:
1. User відкриває форму upload.
2. Вводить title, description, url, обирає файл.
3. Система включає UC9 (validate token → userId).
4. Система валідує формат і поля.
5. Система перевіряє дублікат (`findByAuthorAndUrl` — бізнес-правило, ADR-003 lab3).
6. Система створює `Video` (ER: authorId = userId), повертає 201 + videoId.

Альтернативні потоки:
- **A1** (крок 3): токен недійсний → **401**, кінець.
- **A2** (крок 4): порожній title/невалідні поля → **400**, кінець.
- **A3** (крок 4): invalid video format → помилка зі списком форматів (**REQ11**), кінець.
- **A4** (крок 5): дублікат (authorId, url) → **409**, кінець.

> Ці потоки намальовані як `alt/else` гілки у sequence-діаграмі (Lab 3).

### UC4 Watch Video — актор: Guest (успадковано User) — REQ4

Основний потік:
1. Відкриває сторінку відео.
2. Система віддає player + views + список коментарів.
3. Система інкрементує `Video.views`.

Альтернативні потоки:
- **A1** (крок 2): відео не знайдено → 404.
- **A2**: UC8 може «extend» — перехід із пошуку на перегляд.

### UC5 Comment — актор: User — REQ8, REQ9

Основний потік:
1. UC9 (auth).
2. User пише текст → система створює `Comment` (userId, videoId, createdAt).

Альтернативні потоки:
- **A1**: delete власного коментаря → soft delete (REQ9).
- **A2** (крок 1): 401.

### UC6 Like Video — актор: User — REQ5

Основний потік:
1. UC9 (auth).
2. User клікає like → система створює `Like` (userId, videoId, createdAt).

Альтернативні потоки:
- **A1**: повторний лайк → не створюється (UK-пара з ER); unlike/скасування.
- **A2** (крок 1): 401.

### UC7 Subscribe — актор: User — REQ6, REQ10 (частково)

Основний потік:
1. UC9 (auth).
2. User підписується → `Subscription` (subscriberId, channelId).
3. Система повідомляє власника канала.

Альтернативні потоки:
- **A1**: вже підписаний → скасування/ігнор (UK-пара).
- **A2**: channel owner переглядає список підписників — **REQ10**, покрито частково (не окремий UC).
- **A3** (крок 1): 401.

### UC8 Search Videos — актор: Guest (успадковано User) — REQ7

Основний потік:
1. Вводить запит.
2. Система повертає збіги за title, сортування за relevance.

Альтернативні потоки:
- **A1**: «extend» UC4 — із результатів пошуку йде на перегляд.
- **A2**: пустий запит/немає збігів → пустий список.

### UC9 Authenticate — актори: User/Guest + Google OAuth — REQ2/REQ3

**Роль:** включений («include») у UC2, UC3, UC5, UC6, UC7 — спільна перевірка auth (ADR-003).

Основний потік:
1. Базовий UC викликає UC9.
2. Система валідує token (або credentials → Google OAuth).
3. Повертає userId.

Альтернативні потоки:
- **A1** (крок 2): недійсний/прострочений токен → **401** → базовий UC переривається.
- **A2**: Google OAuth шлях — редірект + callback.
