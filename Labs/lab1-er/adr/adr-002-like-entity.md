# ADR-002: Like — зв'язок чи сутність (MADR)

## Контекст і постановка проблеми

"Користувач лайкає відео" — M:N між User і Video. Питання: моделювати як прямий зв'язок M:N чи як окрему асоціативну сутність Like.

## Розглянуті варіанти

### Варіант 1: прямий зв'язок M:N (`User }|--|{ Video`)

- Плюс: мінімум таблиць, найпростіша модель.
- Мінус: немає куди класти атрибути зв'язку — коли лайк поставлено (`createdAt`) або майбутні (тип реакції тощо). Якщо атрибути не потрібні взагалі — це правильний вибір.

### Варіант 2: асоціативна сутність Like

- Плюс: є місце для `createdAt` і майбутніх атрибутів зв'язку; власний PK; складене `UNIQUE(userId, videoId)` природно лежить на сутності; лайк можна логувати/сортувати за часом.
- Мінус: на одну таблицю більше; трохи складніша модель.

### Варіант 3: сутність без атрибутів

- Формально можливо, але марно — сутність без власних даних нічим не краща за зв'язок.

## Результат рішення

**Варіант 2** — Like як асоціативна сутність. Обґрунтування — не "M:N це помилка" (чистий M:N без атрибутів цілком нормальний), а те, що домен потребує дані про саму подію лайку: `createdAt` (сортування "нещодавні лайки", аудит дій). За тим самим правилом Subscription — теж сутність (має `createdAt`).

## Наслідки

- Like має власний PK (`id`), два FK і `createdAt`; UNIQUE-правило "один лайк від користувача на відео" лежить на парі `(userId, videoId)`.
- Якщо колись час лайку стане непотрібним — модель можна спростити до зв'язку новим ADR.
