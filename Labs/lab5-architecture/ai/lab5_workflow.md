# Lab 5 — AI-Assisted Workflow (methodology)

Документ описує робочий процес, за яким зроблена Lab 5: критерії задачі, стратегія, розподіл ролей між моделями, порядок кроків і правила зупинки. Формат — як у Lab 4, розширений під вимогу «модель інтегрує весь ланцюг».

---

## 1. Критерії задачі (з `task.md`, декомпозиція)

Умова задає п'ять блоків вимог. Кожен крок процесу прив'язаний до критерію — нічого не робиться «для краси».

| # | Критерій з task.md | Де перевіряється | Крок процесу |
|---|---|---|---|
| C1 | Компоненти: UI, API/Backend, сервіси, Data Access, БД | діаграма | draft + spec |
| C2 | Provided/required-інтерфейси визначені | діаграма + spec | notation fix |
| C3 | Залежності | діаграма | draft + audit |
| C4 | Чітка межа системи | діаграма | boundary fix |
| C5 | Зовнішні інтеграції | діаграма | draft + ADR |
| C6 | Рендер з опису | renders/ | build step |
| C7 | Аудит: кожен компонент/залежність трасується до попередніх моделей (дані/вимоги/взаємодія/процес); топ-3 розбіжності | AUDIT.md | trace matrix |
| C8 | DEFENSE: як модель інтегрує весь ланцюг | DEFENSE.md | chain section |
| C9 | Узгодженість з моделлю даних, вимогами, взаємодією, процесом («відмінне виконання») | матриця покриття | P2 + P8 |

Ключова відмінність Lab 5 від попередніх: критерій C7/C9 — **повнота трасування в обидва боки**. Не «діаграма виглядає правильно», а «кожен елемент має джерело в Lab 1–4, і жоден UC не висить без компонента». Це і визначило стратегію.

## 2. Стратегія: trace-first, notation-last

Урок трьох попередніх лаб: викладач оцінює **нотацію окремо від змісту**. Lab 2 відхилена за «граф замість UML», Lab 3/4 — за форму фрагментів. Тому стратегія явно двоетапна:

1. **Спочатку зміст і трасування** — набір компонентів і залежностей має покривати ланцюг. Драфт робиться максимально швидко, навмисно в доступному інструменті — його роль «бути об'єктом критики», не бути фіналом.
2. **Потім нотація** — adversarial-крок обов'язково ставить питання «чи це справжня UML component-нотація?». Відповідь для Mermaid — ні (немає component-стереотипу, lollipop/socket, межі-елемента), тому каноніка — PlantUML. Це третій застосування того самого прецеденту.

Чому не PlantUML одразу: реальна робота йде через помилку. Одноразовий «ідеальний» результат без ітерації — це і є те, за що ловлять «нарисований процес».

## 3. Ролі моделей і чому їх дві

| Модель | Роль | Чому саме вона |
|---|---|---|
| **SWE-2 Max** | генерація: драфт, реалізація фіксів, документи, рендери | сильна на імплементацію; генерує швидко і правдоподібно |
| **GLM 5.3 Max** | рев'ю: чек-листи, adversarial-прогони, матриця трасування, фінальний чек | окремий погляд без авторства; інструкція «fail the draft» працює тільки на моделі, що не писала код |

Принцип: **генератор систематично сліпий до власних дір**. Рознесення по двох моделях — не ритуал: GLM реально спіймав те, чого SWE-2 Max не бачив (untraced Email/SMS Gateway, відсутня матриця покриття). Свою чергою SWE-2 Max як build-роль спіймав на рендері те, чого не бачив текстовий чек-лист GLM (зовнішні візуально всередині межі). Дві моделі = два незалежні детектори різних класів помилок.

## 4. Порядок кроків (як фактично йшло)

```
P1 checklist -> драфт (mmd) -> P2 adversarial+trace -> P3 notation review
-> P4 фікс spec+model (puml) -> P5 render+drawio+самоперевірка
-> P6 AUDIT+матриця -> P7 DEFENSE -> P8 фінальний прогон -> P9 цей документ
```

### Крок 0 — spec-first (`eb61ce7`)

`spec.md` з таблицями компонентів і інтерфейсів ДО будь-якої діаграми. Причина: аудит у форматі «критерій → файл → коміт» вимагає письмових критеріїв; без spec нема чого звіряти.

### Крок 1 — драфт (`ee3c8c3`, `6e1a1d9`)

SWE-2 Max генерує `component.mmd` + ADR-005 з обґрунтуванням Mermaid. Драфт умисно швидкий — містить реальні дефекти, які рев'ю зловить. Це чесний запис процесу: коміти з реальними датами, дифт spec+model разом.

### Крок 2 — adversarial-рев'ю (GLM 5.3 Max)

P1: чек-лист критеріїв → 9 пунктів. P2: прогін кожного пункту з цитатою-доказом + **матриця трасування** (компонент → яке REQ/UC/lifeline/step реалізує). P3: окреме питання нотації — «чи повторюється помилка lab2/lab4?» з поелементним порівнянням. Файндінги → `ai/audit.md`.

### Крок 3 — фікс spec+model одним комітом (`371efc9`)

`component.puml`: `rectangle "VideoHub System"`, `[Component]`-стереотипи, `() Interface` provided/required, зовнішні поза межею. Spec отримує нові критерії (UML-нотація, матриця покриття, Email/SMS як ADR-розширення). `.mmd` видалено — **один канонічний source**. ADR-005 переглянуто: рішення про зміст лишається, інструмент змінено.

### Крок 4 — рендер і синхронізація (`282bf83`)

PNG з `.puml`. **Тут спіймана помилка 4:** перший рендер показав зовнішні всередині межі — PlantUML layout притиснув їх до рамки. Текстовий чек-лист це не бачив — зловило тільки око на PNG. Фікс: `package "External Systems"`. drawio переписано семантично ідентично.

### Крок 5 — документація (`71c9fde`)

AUDIT у форматі рев'ю: критерій → знайдено (цитата) → виправлено → коміт; 5 файндінгів + **матриця UC/REQ/lifeline/activity → компонент** як доказ покриття. DEFENSE — за шаблоном викладача + обов'язковий розділ «інтеграція ланцюга».

### Крок 6 — фінальний прогон (GLM, симуляція чека викладача)

P8: «ти — автоматичний чек викладача, нічого не вважай зробленим без доказу». 9/9 PASS з посиланнями на файли — записано в `ai/audit.md`. Це той самий прогін, що викладач робить своїм пайплайном.

## 5. Як модель «думає» (стратегія всередині промптів)

- **P2 має інструкцію «fail the draft, not approve it»** — без цього рев'юер схильний погоджуватись. Adversarial-framing — головна техніка.
- **Трасування — матрицею, не абзацем.** Таблиця змушує перевірити кожен елемент окремо; пропуск у рядку видно.
- **PASS без цитати не рахується** — кожен вердикт має цитувати рядок файла. Це відрізняє рев'ю від побажань.
- **Критерій → коміт.** Файндінг без коміту = не виправлений. Тому fix-коміти завжди spec+model разом (правило з pre-submit чеку).
- **Рендер — теж артефакт рев'ю.** Помилка 4 доводить: «синтаксис правильний» ≠ «картинка правильна».

## 6. Правила, які процес наслідує (успадковано з попередніх лаб)

| Правило | Звідки | Як застосовано |
|---|---|---|
| Не підробляти дати коммітів | pre-submit check: Events API пале | усі коміти — реальний час роботи |
| Fix-коміт = spec+model разом | рев'ю Lab 1: «без зміни входу не вважається» | `371efc9` — spec + puml + adr одночасно |
| Один канонічний source | «два джерела = розбіжність» | `.mmd` видалено; drawio/png — похідні |
| «Умова дозволяє обидва» ≠ «обидва прийнятні» | відхилення Lab 2 | PlantUML як каноніка, не Mermaid |
| Untraced ≠ видалити | практика Lab 4 | Email/SMS лишено з ADR-обґрунтуванням |

## 7. Стоп-умови (коли лаба «готова»)

- Чек-лист P1 — усі 9 пунктів PASS з доказом файл/елемент (записано в `ai/audit.md`).
- Матриця покриття повна: **жоден компонент без сліду, жоден UC1–UC9 без компонента** — обидва напрямки.
- Один канонічний source `.puml`; PNG перевірений оком; drawio — валідний XML.
- Кожен файл AUDIT-файндінга має реальний хеш коміту (`git show` не падає).
- `git status` чистий; вітка запушена.

| Крок | Піймав/дав |

Висновок: жодна модель не зробила б це сама. Драфт був правильним за змістом і хибним за нотацією; рев'юер не писав код, але знайшов структурні діри; рендер-перевірка зловила візуальний баг поза текстом. Три детектори — три класи помилок.
